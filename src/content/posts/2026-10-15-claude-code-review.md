## 推文全文翻译

## 一句话总结

AI 写代码多到人看不过来时，Claude Code 团队没有取消评审，而是把「逐行阅读」交给多层自动检查（自验证 → AI 评审 → 安全评审 → CI → 按风险分级的人工审批 → 合并队列/灰度 → 快速回滚），把人的时间留给「该不该做、风险、架构、看证据、对结果负责」这几件机器做不好的事，并用回滚率和事故率做护栏。

## 核心要点

- **数字背景**：Claude 写了约 90% 的 Claude Code 代码；6 月到 9 月合并 PR 翻倍多，回滚占比降 40%+；Anthropic 大仓库每天落地的改动从 5 月约 2,500 个涨到 9 月 30,000+ 个。
- **重新定义评审**：问题不是「有没有人读过代码」，而是「这次改动可能出什么错？由哪种检查（自动或人工）来抓最合适？」
- **评审从「终点关卡」变成「持续进行」**：像写字时的拼写检查一样，人被叫来之前，Claude 通常已经评审并修过至少一轮。
- **稀缺资源是人的时间和注意力**：既包括评审花的时间，也包括修坏代码花的时间；只砍前者、后者增加，等于没省。
- **目标**：Claude Code 各仓库（CLI、桌面/网页端、移动端）大多数 PR 最多一个人参与（可以就是作者本人），且回滚和事故不增加。
- **度量**：每个 PR 的人工审批数（中位数和 P95）、人工评论数、PR 等人的时长；回滚率/事故率是护栏。
- **七层防线**：自验证、每个 PR 的 AI 评审、可阻断的安全评审、可阻断的 CI、按风险分级的人工审批、合并队列 + 功能开关 + 渐进发布、快速发现 + 快速回滚。
- **评审器自身也要被评审**：把历史事故做成每天跑的评测集；用人的反应衡量噪音；限制评审轮数让「AI 写 + AI 审」能收敛。
- **人留在五类决策上**：该不该做、高风险代码、会被模仿的架构、读懂证据、对结果负责。
- **文化**：「谁合入谁负责」，但不是追责；改动小、可回滚、按影响范围定门槛；在公开频道协作。

## 分节讲解

### 0. 开篇：Claude 写 90% 的代码，那还有人读代码吗？

- 文章开头抛出三个问题：产出这么多代码怎么评审？还有人读代码吗？出问题谁来抓？
- 结论先行：他们**没有取消评审**，而是做了三件事——把大部分「阅读」交给机器；围绕人的时间与注意力来优化；大力投资「让犯错能快速、轻松地撤销」。
- 成绩：6–9 月合并 PR 翻倍多，回滚占比降 40% 以上。

### 1. 重新思考代码评审的目的（Rethinking the purpose of code review）

- Agent 写代码后改动量暴涨：Anthropic monorepo 每天落地的改动从 5 月约 2,500 到 9 月 30,000 以上。Claude Code 有独立仓库，但压力同样大。在这种速度下，人工逐行评审几乎不可能。
- 代码评审本来有**两项职责**：① 在上线前发现并修复问题；② 在团队中建立共享上下文、加深对代码库的理解。本文主要讲 ①，② 在后面「团队共享上下文」一节讲。
- 关键观点：原文说 *"did a human read the code?" is an imprecise proxy* ——「有人读过代码吗？」只是一个不精确的替代指标，真正该问的是「这次改动可能出什么错，哪种检查最适合抓住它」。
- 时间点也变了：以前评审是流程末端的关卡（写代码 → 开 PR → 等同事）；现在评审**持续进行**，像拼写检查。大多数改动在人看之前已被 Claude 审过并修过一次，常规错误基本被挡掉，团队注意力留给更高层的问题。

### 2. 稀缺资源：人的时间和注意力（The scarce resource）

- 人的时间要花在只有人能解决的问题上，其余交给自动检查。即便自动化程度这么高，团队几乎每天都碰到新问题，人依然很忙。
- 「人的时间」包括评审的两面成本：**审代码的时间** + **修坏代码的时间**。前者减少但后者增加 = 只是把成本挪了地方。
- 目标：Claude Code 仓库的大多数 PR 合并时**最多一位人类参与（可以是作者本人）**，且回滚和事故不增加。
- 度量指标：
  - 每个 PR 的人工审批数（中位数和第 95 百分位）
  - 人工评论数
  - PR 等待人处理的时长
  - **护栏**：回滚率和事故率——一旦上升，说明没有真正省下时间，只是转移了。

### 3. 一次改动的生命周期（The life of a change）

- 一次典型改动从工程师的电脑（或 Slack 里的一个 Claude 会话）出发，要经过多层评审才到用户手里。
- 原文配图要点：路径大部分是自动化的，人的注意力只投向风险所在。

### 4. 逐层讲解（Layer by layer）

总思路：**不是一道关卡，而是多层过滤**。每一层都会漏掉一些问题，但很少有问题能穿过所有层；漏网之鱼由回滚兜底。

#### 第 1 层：别人看之前，工作先被验证

- 大部分评审现在发生在 PR 创建**之前**。
- 给 Claude 一个它能「跑」的东西：测试、构建、或一张和设计稿对比的截图，并要求它**展示输出结果，而不是只说「做完了」**。
- 然后让一个**拥有全新上下文的子 agent（subagent）**来审 diff。这两条都出自他们的最佳实践指南。
- 开 PR 前，很多人还会跑几个内部 skill：一个专门找 bug、一个简化 diff、一个做端到端行为检查；UI 改动还要对照设计规范检查。
- Claude Code 作者 Boris Cherny 认为：给 Claude 一个验证自己工作的手段，可能是获得好结果**最重要的一件事**，大概能让最终结果好 2–3 倍。验证方式因领域而异：可能是一条 bash 命令、一套测试，或在浏览器/手机模拟器里试用。
- **在源头修复重复问题**：如果自动评审一再标出同一类问题，就去改 skill、加 lint 规则，或更新说明文件：
  - `CLAUDE.md`：告诉 Claude 这个项目是什么——技术栈、约定、目标与非目标。每次评审都会加载它，所以大仓库里要写**短**，其他内容用链接指向别的文档。评审器还会标出违反其中约定的代码，以及让其中某行变过时的改动。
  - `REVIEW.md`：由代码负责人（code owners）写，告诉评审器在他们负责的代码里什么最重要。团队会另外检查评审器是否真的遵守它。好的 `REVIEW.md` 特点：
    - 短；
    - 说清楚这个仓库里「失败」长什么样（文档的失败是「它在撒谎」，配置的失败是「它把流量导错了地方」）；
    - 限制挑刺（nit）的数量；
    - 列出可跳过的路径；
    - 要求给出**文件和行号作为证据**，而不是凭名字猜测；
    - 要求总结以「问题数量」开头，没问题时直接说没问题。

#### 第 2 层：每个 PR 都有 AI 评审

- 人看之前，每个 PR 都先过一遍 Claude 评审。它结合**整个仓库**和 PR 的**声明意图**来读 diff，问三件事：改动是否解决了它要解决的问题？是否契合系统？是否弄坏了别的东西？修 bug 时会追查根因。
- 公开产品叫 **Code Review for Claude Code**，已在 Team 和 Enterprise 计划正式可用（GA）；本地的 `/code-review` 命令是轻量版。
- 研究预览上线后，内部 PR 中收到「实质性评审意见」的比例从 **16% 升到 54%**。超过 1,000 行的 PR 大多有发现，小 PR 大多是干净的。
- 管理员可把每个仓库设成 **Quick / Standard / Deep** 三档。漏一个 bug 的代价大于多花的评审时间时，就用 Deep。
- **发现要先被其他 agent 验证**才给人看：
  - 多个 agent 同时找 bug；
  - 另一组 agent 对每条发现**投票**，足够多的 agent 认为是真问题才发出来；
  - 只涉及风格、诊断信息或清理的发现会被丢弃；
  - 这些过滤规则先在自家 PR 上做过 A/B 测试才保留。
- 留下的发现以行内评论形式出现，按严重程度排序，每条带标签：**Important（重要）/ Nit（挑刺）/ Pre-existing（原本就有）**——这样不是本 PR 引入的老 bug 不会显得像作者的锅。
- **每条发现都必须回应**：要么修，要么写理由关闭讨论。常常有 agent 夜里接手修复，作者第二天回来时 PR 已经又过了一轮。

#### 第 3 层：可以阻断合并的安全评审

- 安全有独立的自动评审。只要 bug 评审或安全评审中还有**未解决的发现**，PR 就不能合并。
- 处理误报的方式：写一句简短理由关闭讨论。后续提交修复了问题，发现会自动清除。
- 自己可用的工具：开源的 security review GitHub Action，或 `/security-review` 命令。

#### 第 4 层：会阻断的自动检查（CI）

- 常规项：lint、类型检查、在所有平台上跑测试、构建。一个典型 CLI PR 在人看之前可能要跑几十项检查。
- **PR 模板**要求写明：这次改动怎么测试的、怎么撤销。Claude 可以帮填，但**提出这次改动的人要签字确认**。

#### 第 5 层：按风险分级的人工审批

改文档和改自动更新器风险完全不同，所以审批强度不同：

- **低风险**（文档、文案、仅内部功能、藏在开关后的增量改动）：自动评审和安全检查全绿后，**不需要人工审批**。
- **中风险**（普通产品改动；以及缓存、自动更新器、系统提示词等敏感区域）：**1 人**审批。
- **高风险**（最高风险代码，以及一小批永远要两人的路径）：**2 人**审批。

几条关键规则：

- **风险等级由改动决定，不由作者决定**。一个分类器读改动、定等级；第二个分类器再判断「这个具体改动是否即使等级不要求，也需要多一个人看」。owners 列为敏感的路径和任何 CI workflow 文件，**永远需要人**。
- **只有受信任作者能走轻量通道**：只有在仓库受信任名单上的作者（主要是拥有该仓库的团队）能走轻路径，其他人一律需要第二个人审批。
- **agent 的批准永远不等于人的批准**：自动评审能放行低风险改动，但不能占用「需要人」的审批名额。
- **谁发起谁负责**：agent 写的 PR，指挥 agent 的那个人算作必需评审人之一，就像代码是他自己敲的。
- **审批只对应某一个具体提交（commit）**：之后出现系统无法担保的新提交（比如 agent 推送、有人手动解决的合并冲突），必须重新审批。

#### 第 6 层：合并队列、功能开关与渐进发布

- **合并队列（merge queue）**：把改动应用到 main 上重新跑所有检查，防止「两个 PR 各自都通过、合起来却把 main 弄坏」。
- 新行为通常先藏在**功能开关（feature flag）**后，先给 Anthropic 员工用；员工的重度使用往往比用户更早暴露回归问题。
- 公开发布先进 `latest` 渠道，`stable` 渠道滞后跟进。

#### 第 7 层：快速发现、快速回滚

- 总会有错误漏过去，所以最后一层的目标是**尽快发现**。功能开关不用发版就能关掉。
- Claude Code 有每周轮值的 on-call；事故复盘会问：「本该由哪一层抓住它？」
- 现状与不足：发现坏合并仍依赖作者、on-call 以及回滚/事故看板。他们**还没有**「熔断器」（这些指标变差时自动收紧审批），工程师希望在更多代码走向「零人工合并」之前先把它做出来。
- 一位同事的观点：放慢速度确实能降低错误率，但主要是因为你什么都做得更少了。团队宁愿更快地发现和修复问题。

### 5. 怎样让评审器变得更好（How we make the reviewer better）

评审流程本身在一个持续改进的循环里：

- **每次事故都变成一条评测（eval）**：收集历史上引发事故的 PR（连同后续修复和回滚），让熟悉那段代码的工程师确认每个 bug 及其位置。评审器**每天**跑一遍这个集合；每个事故都让集合变大，评审器的每次改动都要在整个集合上打分。
- **用人的反应来衡量噪音**：多报很容易提高抓 bug 数，所以要有制衡。把评审器的每条评论按 PR 上的人怎么回应分类：修了 / 说它错了 / 说这是有意为之 / 认为无关紧要。另外在**已知干净的 PR** 上跑评审器，统计它有多少次报出「会诱导人做出有害改动」的问题。书面优先级：**先抓真 bug，其次减少评审轮数**。
- **作者是 agent 时噪音更贵**：人几秒就能忽略一个 nit；agent 会去「修」它，于是又多一个提交、又多一轮评审。
- **评审必须收敛**：agent 作者和 agent 评审能互相无限忙下去——有个 CLI PR 一夜间来回了 50 多轮，最后作者手动叫停。
  - 用 git blame 分析评审器反复标出的问题：约 **59%** 是评审器第一轮时就已存在的代码。也就是说它很少发现新 bug，而是每轮多挖出几个老问题。
  - 团队自己也有责任：习惯了默认跑好几轮（每轮总能抓到点新东西）。高风险改动值得，但不是每个 PR 都值得。
  - 现在把「通过所需轮数（rounds-to-pass）」和召回率（recall）一起跟踪，并改了重审规则：
    - **轮数上限**：3 轮之后，评审器请作者退一步重新考虑整体方案；
    - 前几轮之后**只审新增 diff**；
    - **标出 bug 的类别**，让作者修掉所有同类实例，而不是只修一行；
    - **不重复**已经发过的发现。
- 评审 agent 还会**每晚扫描已有代码**，在老 bug 冒出来之前抓住它们。原文配图显示改动后每个内部 PR 的评审轮数下降。

### 6. 人在哪些环节保留决策（Where humans stay in the loop）

把资深工程师从深度工作中拉出来抓一个常规错误，比自动评审贵得多。人的工作从「读每个 diff」变成了机器不擅长的五类决策：

- **该不该做**：方向、品味、范围。有个团队宣布评审瓶颈已解决，但仍对**团队外部**来的改动保留人工评审，好让有人问一句「我们真的该做这个吗？」
- **高风险代码**：计费、自动更新器、CI workflow。
- **会立模式的架构**：别人会照着抄的设计。
- **读懂证据**：测试输出、执行的命令及返回、截图、评审器的发现。原文建议：如果你说不出这些检查会漏掉什么，就去要一次真正的评审，而不是随手批准。
- **对结果负责**：每个上线的改动都有一个人为它负责，不管是谁敲的代码。

### 7. 在团队中共享上下文（Sharing context across the team）

- 评审的第二职责是传播对代码库的理解。如果机器读了大部分代码，人怎么学习代码？
- 他们没有正式流程。没人在脑子里装着 Claude Code 的完整模型，他们也认为没必要。
- 想了解某部分代码时，**让 Claude 为这一小块写一份讲解（explainer）**，几分钟搞定，且反映当前代码的真实状态。有人更进一步，让 Claude 做一个小型可视化 artifact，按自己喜欢的学习方式讲这块代码。
- 对比：逐行读一个一行的文案改动几乎学不到东西；而在改某个模块前读它的讲解，收获大得多。
- 默认在**公开 Slack 频道**工作的文化也有帮助：别人在做什么，你在他们做的过程中就看得到。

### 8. 「谁合入，谁负责」（"You land it, you own it"）

团队规范：你合入的中小改动出了问题，通常由你来修。几条保障让它不至于变坏：

- 改动**小**，易审、易调试、易回滚；
- **一切可撤销**：开关、回滚、分阶段发布能在几分钟内撤销大多数错误；
- **影响范围（blast radius）决定门槛**：代价高的代码配更多人、更多检查；
- 回归问题通过遥测和内部使用**很快暴露**；
- **不是追责**：由你修是因为你上下文最多；事故复盘看的是系统问题。
- 所有权也是**共享**的：在公开频道里任何人都能看到别人在做什么、接手一条线索，或派一个 Claude 去补缺口；不拥有代码的人也会给反馈。这种开放是「不对每一行设关卡也能保持质量」的重要原因。

### 9. 当我们改变方向时（When we change direction）

- Agent 让「开始做一件事」变得很便宜，所以有些工作**不该合入**。通常频道里有人问「为什么要做」、指出之前的决定，或建议更简单的路线，作者就关闭或重塑 PR。
- 代码写得快，关掉 PR 也不心疼。诀窍：**尽早**在讨论里提出不同方向，而不是在已完成的 PR 上留一条阻断性评论。

### 10. 你可以怎样采用这套流程（How you can adopt this process）

原文说大部分组件今天就能用上。按阶段整理：

**① PR 之前**

- 给 agent 可运行的检查，写在一个**简短的 ****`CLAUDE.md`** 里；再配上运行格式化工具和 linter 的 hooks。
- 在本地跑 `/code-review` 和 `/security-review`，或用一个全新上下文的子 agent 做评审。
- 加一个 `REVIEW.md`，把反复出现的评审意见沉淀进去。

**② 每个 PR**

- 强制 CI；在 PR 模板里加「Testing（怎么测的）」「Risk（风险）」「How to revert（怎么回滚）」。
- 先在**一个仓库**上加 AI 评审器（Code Review for Claude Code 或 Claude Code GitHub Action），花几周调 `REVIEW.md`，再推广。
- 加自动安全评审，并要求**所有评审讨论都解决**才能合并。
- 评审力度匹配风险：常规改动快速过，漏 bug 代价高的地方深审（Code Review 里的 Quick / Standard / Deep）。
- 限制评审轮数；前几轮之后只重审新 diff。

**③ 审批**

- 把风险等级**写下来**，按改动而不是作者来定；**先严后松，用证据放宽**。
- 轻量审批通道只给信任的作者。
- 用 **CODEOWNERS** 和**分支保护**，让认证、计费、CI 与发布 workflow、安装器永远需要人审。
- 机器人的批准永远不能替代必需的人工批准；有新提交时作废旧批准。

**④ 合并与之后**

- 用合并队列、功能开关、先内部使用、分阶段发布、一步回滚。
- 把事故和回滚做成评测集；评审器的提示词、工具或模型一变就重新打分。
- 度量人的时间，以回滚率和事故率为护栏。

### 11. 未来走向（Where this is going）

- Code Review 产品的立场：批准 PR 仍是**人的决定**，产品只发「发现」，不发「批准」。
- 但他们自己的仓库更进一步：让 owners 决定哪些低风险改动只靠自动检查就能合并，这条线还在不断移动。
- 评审漏了东西时，他们会问「模型当时缺了什么信息」，然后把修复写进 `CLAUDE.md`、某个 skill 或一项新检查。
- 目标不变：**每个改动花更少的人类时间，且回滚不比以前多**。
- 结尾邀请读者分享：你们自动化了哪些检查、哪些还需要人、以及觉得他们哪里做错了。

## 和我前端工作 / 项目的关联

我的项目（/shutter 快门计数、EasyPic、菜谱站）基本是「一个人 + Cursor/AI 工具」开发，团队规模不同，但这套思路可以按比例缩小来用：

- **先给 AI 一个能跑的验证手段（最值得马上做）**
  - /shutter：准备几张已知快门数的样例照片（不同品牌的 EXIF），写成测试用例：上传 → 解析 → 断言结果。让 Cursor 改完解析逻辑后**必须跑测试并贴出输出**，不接受「我改好了」。
  - EasyPic / 菜谱站：UI 改动让 AI 用 Playwright 截图，和设计稿或上一版截图对比（视觉回归）。对应文中「拿截图和设计对比」。
- **写一个短的项目说明文件**：在每个仓库放 `CLAUDE.md`（或 Cursor 的 `.cursor/rules` / `AGENTS.md`），写清技术栈、约定、目标与非目标，以及「改完要跑哪些命令」（如 `pnpm lint && pnpm typecheck && pnpm test && pnpm build`）。保持短，详细文档用链接。
- **把我反复提的意见沉淀成 ****`REVIEW.md`**** 或 lint 规则**：比如菜谱站「图片必须有 alt」「不许直接写死 OSS 域名」「移动端断点要测」。同一类问题出现第二次，就加规则或 ESLint 规则，而不是每次口头提醒。
- **开新上下文做评审**：写完后开一个新的 Cursor 对话/新 agent，只给 diff 和项目说明，让它找 bug；和工作日志里「试行写码/审码双 agent 分工」的待办直接相关——本文正好给了落地细节：评审意见要带文件和行号、分 Important/Nit/Pre-existing、限制 nit 数量、**最多 3 轮**，之后重新考虑方案，避免两个 agent 互相刷轮次。
- **按风险分级自己的审批**：
  - 低风险（文案、菜谱内容、样式微调）：CI 全绿 + AI 评审无 Important 就合并。
  - 中风险（/shutter 解析逻辑、上传接口、EasyPic 图片处理）：我亲自看一遍证据（测试输出、截图）。
  - 高风险（Nginx 配置、部署脚本、GitHub Actions workflow、OSS 密钥/权限相关）：永远我亲自审，可在 GitHub 用 CODEOWNERS + 分支保护强制。
- **PR 模板加三栏**：怎么测的 / 风险 / 怎么回滚。AI 可以帮填，我签字确认。
- **让撤销变便宜**：新功能加功能开关（哪怕是一个环境变量或配置项）；部署保留上一版，做到一条命令回滚；先自己用（相当于「内部先用」）再公开。
- **用事故喂评测**：/shutter 某个机型解析错了，修好后把那张样例图加进测试集——这就是个人版的「事故即评测」。
- **学代码用讲解代替逐行读**：接手旧模块时（比如半年前写的 EasyPic 压缩逻辑），让 AI 写一份这块代码的讲解或画个流程图，和系统设计第 1 周的 /shutter 流程图练习可以互相配合。
- **度量**：简单记录「合并了多少 PR、回滚了几次、线上出了几次问题」，看引入 AI 评审后回滚是否下降。

## 自测题

1. 文章认为「有人读过代码吗？」为什么是一个不精确的指标？它应被替换成什么问题？
   
参考答案

   因为读没读过不等于风险被覆盖。应问：「这次改动可能出什么错，哪种检查（自动或人工）最适合抓住它？」

2. 团队如何衡量「省下了人的时间」？为什么要把回滚率和事故率作为护栏？
   
参考答案

   看每 PR 人工审批数（中位数、P95）、人工评论数、PR 等人时长。人的时间包含评审时间和修坏代码的时间；如果回滚/事故上升，只是把时间从评审挪到了修复，并没省。

3. AI 评审如何降低噪音？列出至少三种机制。
   
参考答案

   多个 agent 并行找 bug，另一组投票确认才发布；丢弃纯风格/诊断/清理类发现（经 A/B 测试）；按严重程度排序并打 Important/Nit/Pre-existing 标签；用人的回应分类和「已知干净 PR」测误报；`REVIEW.md` 限制 nit、要求文件行号证据。

4. 为什么「agent 写 + agent 审」可能不收敛？团队做了哪四项改动？
   
参考答案

   双方会无限来回（有 PR 一夜 50+ 轮），且约 59% 的被标问题是首轮就存在的老代码。改动：3 轮上限后请作者重新考虑方案；前几轮后只审新 diff；标出 bug 类别让作者一次修全；不重复已发的发现。

5. 风险分级审批中，「等级由改动决定而非作者」以及「agent 批准不能代替人」分别防止什么问题？
   
参考答案

   前者防止资深/自信的作者把高风险改动走轻量通道（由分类器按改动定级，敏感路径和 CI workflow 永远要人）；后者保证需要人的审批名额必须由真人担责，自动评审最多只能放行低风险改动。
