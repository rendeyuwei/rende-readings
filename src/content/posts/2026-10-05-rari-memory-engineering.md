## 要点速览

1. 团队 Bot 要学会“每个人怎么干活”，但不能把某个人的对话变成所有人的记忆。
2. 上下文分五类：实时数据源、团队技能、团队记忆、个人笔记、任务状态，各放各的地方。
3. 存“结论”，不存“对话”；进团队记忆前先问清：谁说的、去哪核实、谁负责、是否批准、何时复查。
4. 变化快的事实（状态、余额、价格、权限、指标）不进记忆，每次去源头查；稳定的（口径、定义、流程归属）才记。
5. 记忆是“知道什么”，技能是“会做什么”；流程应写成由负责人维护的技能。
6. 共享知识 ≠ 共享身份：个人 OAuth 用提问者自己的账号，Bot 级密钥等于全队权限，要最小授权。
7. 在 Slack 频道回答前先看受众，私密细节挪到一对一聊天。
8. 上线前用两个真实账号测五种情况：私密泄露、显式共享、过期事实、互相矛盾、频道边界。

## 前言

个人 AI 助理能记住你喜欢怎样的报告格式。团队 Bot 的活更难：它要学会每个人的工作方式，又不能把一个人的对话变成所有人的记忆；要分清哪些决定是共享的、哪些偏好是私人的、哪些事实必须回源系统再查一遍。

这正是 Grok Bot 新推出的团队 Bot（Team Bots）有意思的地方：一个 Bot 可以配好共享文件、技能、插件和记忆，再发布给团队在 app 或 Slack 里用（目前面向 Teams 和 Enterprise 计划公测）。

但“一个 Bot 给所有人用”不等于“所有人共用一份聊天记录”。一对一聊天里每人的对话是私密的；团队记忆共享；个人笔记只属于本人；通过某人账号登录的插件用的是提问者的权限，不是创建者的；Slack 共享线程和 Bot 级密钥又是另一套边界。这是真正的架构，不是一个记忆开关。配置不好，Bot 不只是会忘事，而是会学错、记错地方，或者把旧决定套到新情况上。

## 记忆工程，说人话

记忆工程就是决定 Agent 应该把什么带到下一份工作里。不是“全都存”，不是“总结最近 100 条消息”，也不是“把公司 wiki 塞进系统提示”，而是一条从“有用的观察”到“可复用的工作上下文”的受控路径。

好的记忆让下一个人不用重复做同一个决定；坏的记忆会悄悄取代真正的权威来源。区别不在存了多少 token，而在规则：什么能进记忆、谁能读、什么时候不再可信。

## 团队 Bot 改变了“纠正一次谁受益”

以前教个人 Bot，主要改进的是你自己以后的对话；现在一次共享的纠正能改进下一个同事的对话。边界情况就来了：

- “给我的进度汇报短一点”是个人偏好；
- “事故负责人是值班工程师，不是产品经理”可能是团队规则；
- “转化率口径上周二改了”既不是偏好也不是永久规则，而是一个会变的事实，应该放在权威系统里。

Grok Bot 文档说得很清楚：团队记忆所有人的对话都会读，个人有自己的私人笔记；有人说“全队都该知道这个”时，Bot 才把它存进团队记忆，并告诉对方。工程问题在于：大家**应该**让它共享什么。

SpaceXAI 自己的 Data Bot 是个好例子：它用只读的数据仓库凭证和围绕 4.5 万多张表的技能库。它不需要背下这些表，需要的是找到对的表的技能、实时查询的权限，以及能让下一个同事受益的纠正记忆。本文要讲的就是：**可复用的判断放记忆，会变的数据留在源头。**

## 别把所有上下文都当记忆

把 Bot 的上下文分成五个桶：

```javascript
LIVE SOURCE      实时数据源：Linear、Datadog、CRM、文档或代码里的当前事实
TEAM SKILL       团队技能：Bot 负责人批准的可重复流程
TEAM MEMORY      团队记忆：共享的决定和稳定的定义
PRIVATE NOTE     个人笔记：某个人的偏好和工作背景
TASK STATE       任务状态：这一次运行正在做什么
```

团队的事故处理流程属于技能；当前事故等级属于事故工具；大家约定的“影响客户”的含义可能属于团队记忆；你喜欢的简报格式属于个人笔记；今天排查中的未决问题属于任务状态。

把会变的指标放进团队记忆，它会过期；把全队规则放进个人笔记，别人拿不到；把个人偏好放进团队记忆，Bot 就会强加给所有人。记忆工程的第一件事就是把上下文分到对的桶里。

## 晋升的是“事实”，不是“对话”

假设同事说：“新的上线清单要求外部 API 变更发布前做安全评审。”这至少有四种可能：只是提议还没批准；已批准的团队流程；只适用于某个产品；上个月是真的但清单又改了。只存这句话，就丢掉了关键区别。

作者建议对任何可能进入共享记忆的内容，先在外部填一张评审卡（这是流程示例，不是 Grok Bot 配置语法）：

```javascript
claim: "External API launches need security review"   # 主张
scope: team                                            # 范围
source: "link to the approved launch checklist"        # 来源
owner: "security-eng"                                  # 负责人
status: approved                                       # 状态
review_after: "2026-11-01"                             # 复查日期
```

重点不是格式，而是背后的问题：谁说的？去哪核实？谁负责这条规则？批准了吗？什么时候过期或复查？

如果团队把这些卡放在自己的仓库里，一个小脚本可以在人工审核前挡掉不完整或过期的候选（它查的是外部台账，不是 Grok Bot 的记忆接口，也证明不了内容是真的）：

```py
from datetime import date, timedelta

def eligible_for_review(card: dict) -> tuple[bool, str]:
    for field in ("claim", "source", "owner", "review_after"):
        if not card.get(field):
            return False, f"missing {field}"
    if card.get("scope") != "team":
        return False, "wrong scope"
    if card.get("status") != "approved":
        return False, "not approved"
    try:
        review_date = date.fromisoformat(card["review_after"])
    except (TypeError, ValueError):
        return False, "invalid review date"
    if review_date <= date.today():
        return False, "review date passed"
    return True, "inspect source before saving"
```

输出只是一个待审队列，不是写入团队记忆的许可。还得有人打开来源确认主张、范围、负责人都对，然后让 Bot 存“批准后的规则”，而不是产生它的讨论：

```javascript
Save this for the whole team:
For external API launches, check the current launch checklist
and get the required security review before publishing.
The checklist remains the source of truth if the process changes.
（为全队保存：外部 API 上线前查当前上线清单并完成所需安全评审；流程变了以清单为准。）
```

最后一句很关键：记忆是一个指针加一条工作规则，不是公司资料的永久副本。

## 共享记忆需要一条“写入路径”

当所有人都能教同一个 Bot，“记住这个”就成了有后果的写操作。给它一个简单约定：

```javascript
OBSERVE（观察） → CLASSIFY（分类） → VERIFY（核实） → PROMOTE（晋升） → RECHECK（复查）
```

- 观察：同事纠正 Bot、改了流程或确认了决定；
- 分类：是个人的、全队的、任务相关的，还是实时事实？
- 核实：Bot 能指向某个决定、文档、PR、工单或负责人吗？
- 晋升：只把有用的结论存到对的范围；影响团队政策的要先批准；
- 复查：做重要动作前或到复查日期时，重新打开来源。

这是建议的操作模式，不是 Grok Bot 自动帮你跑的流水线。产品提供团队记忆和个人记忆，存什么仍由你决定。

## 权威来源必须留在记忆之外

很多 Agent 记忆演示在这里翻车：Bot 记住某客户是企业版；客户降级了；两周后 Bot 凭记忆批准了一个该账户已不允许的请求。记忆完美地完成了任务，架构却失败了。

Grok Bot 自己的指南也说：记忆不能替代权威来源，会变的事实应留在源系统，重要决定应重新打开或引用当前数据。作者把记忆分成两种时钟：

```javascript
SLOW CLOCK（慢时钟）  语气、定义、归属、稳定流程   → 可以记
FAST CLOCK（快时钟）  状态、余额、价格、负责人、权限、指标 → 每次去取
```

规则很简单：如果搞错它会改变一个动作，那就在行动前查实时来源。比如团队 Bot 可以记住团队怎么分诊 bug，但在宣称 bug 已修好之前，仍应重新打开当前 Linear 工单、最新 Datadog 链路和关联 PR。

## 团队技能不是团队记忆

记忆是 Bot“知道什么”，技能是 Bot“会做什么”。“本团队 P0 指全客户宕机”是定义，可以进团队记忆；“收到 P0 告警时看哪些看板、开事故、呼叫谁、发什么更新”是流程，应该做成团队技能。

在 Grok Bot 里，普通成员可以在私聊里教一个流程，但这不会变成全队技能。共享配置由负责人维护；9 月 30 日的更新允许创建者指定管理员，也能修改技能、插件、密钥和 Slack 应用。这道“维护者关卡”很有价值，否则一次性的变通办法会悄悄变成所有人的默认流程。

Grok Bot 开发者 Lauren Tan 对反复出现的纠正有个原则：先消除根本故障，再考虑加一条指令。优先级是：能改架构就改架构，其次把反复出现的错误写进测试，最后才加技能或规则。作者推论：对一直犯同样错误的系统，记忆不该是第一块补丁。

每个新技能都应满足：解决可重复的工作而非单张工单；输入输出可见；权限边界清楚；有人负责更新；失败时留下证据，而不是静默重试。

## 共享知识不等于共享身份

这是这次发布最重要的安全细节：团队 Bot 可以用共享上下文，同时以提问者的身份行动。

```javascript
PERSONAL OAUTH       个人 OAuth：动作用提问者自己的账号
BOT SERVICE KEY      Bot 服务密钥：动作用 Bot 级共享权限
PRIVATE CHAT         私聊：私密对话和笔记
SLACK CHANNEL        Slack 频道：共享线程和共享的 Bot 电脑
```

区别在凭证，不在插件名字。用 OAuth 配置的共享插件仍以提问者账号运行；用 Bot 级密钥配置的插件，所有人用同一个凭证，所以密钥应按团队所需的最小权限来设。

在 Slack 共享线程或群聊里使用同事的个人连接器前，Grok Bot 会先询问并说明会用哪个账号；已在 Bot 上配置好的共享插件不会触发这个提示。9 月 29 日还新增了只有相关人员能回应的 Slack 操作审核卡片。

“Bot 知道”和“Bot 可以做”是两回事：它可能知道退款流程，但不应推断每个同事都能批准退款；它可能知道机密文件在哪，但不应因为有人在公开频道提到就贴出来。**记忆决定有什么上下文可用，权限决定允许做什么动作，两道检查都要有。**

## Slack 带来第二道记忆边界

Slack 里的团队 Bot 感觉像一个同事，但底层上下文取决于对话发生在哪：一对一聊天里有自己的对话和私人笔记；频道里线程是共享的，Grok Bot 为这个 Bot 用一台单独的共享电脑。文档提醒不要把不该让全频道看到的内容放进频道线程。

一个隐蔽的失败模式：有人在频道里问了个无害问题，并允许 Bot 用他的个人连接器。账号边界没破，但回答里可能带出频道其他人不该看到的细节。批准访问一个来源，不等于批准从中披露任何内容。解决办法不是“告诉模型小心点”，而是把“发到哪里”纳入检索和输出策略：

```javascript
在共享频道回答前：
1. 确认这个线程的受众
2. 确认来源及其访问范围
3. 只总结这些受众可以看到的内容
4. 私密细节挪到一对一对话
```

这是操作建议，不是 Grok Bot 内置保证。更安全的默认是：敏感排查放私聊，只把批准后的结论发给团队。

## 为矛盾而设计，不只为回忆

两个人说法不一时，团队记忆就难了。销售说续约日是 14 号，财务说 30 号，CRM 写 28 号。天真的 Agent 选最近的那句；有用的 Agent 会问这是哪类事实、它存在哪。续约日是合同实时事实，CRM 也可能错，所以行动前应查已签合同或问负责人。

对每条值得保留的共享记忆，把决定和出处记在团队能查看的地方（文档、issue 或轻量台账），Bot 的记忆指向它。出现矛盾时按这个顺序：停下重要动作 → 找到权威来源 → 请负责人解决冲突 → 先更新来源 → 再修正或删除 Bot 记忆。这是记忆维护，不是调提示词。

## 一个实用的团队 Bot：发布协调

设想一个产品、工程、客服共用的团队 Bot，在发布频道里回应 @ 并帮忙准备上线简报。（默认团队 Bot 不回应频道里每条顶层消息；要盯整个频道需要单独的监听 routine，归设置它的人所有。）

- 周一：产品确认只对付费团队上线 → Bot 可以记住这个决定，并指向发布计划；
- 周二：工程改了上线日期 → Bot 应读当前发布工单，而不是信周一的日期；
- 周三：客服说内部简报要更短 → 可以成为维护中技能里的客服专用指令，不应悄悄变成所有人的格式规则；
- 周四：安全负责人批准新增一个评审步骤 → 由 Bot 负责人或指定管理员更新共享上线技能；
- 周五：有人在 Slack 问“可以宣布了吗？” → Bot 应先收集实时证据：

```javascript
release ticket     发布工单：当前日期和灰度状态
launch checklist   上线清单：需要的审批
PR and CI          PR 和 CI：构建与验证状态
team memory        团队记忆：已批准的受众和决策历史
private notes      个人笔记：不要用于共享频道的回答
```

作者希望在共享线程里看到这样的回答：

```javascript
STATUS: Blocked, do not announce yet      状态：受阻，暂不宣布
CHECKED: Current release ticket, launch checklist, CI run   已检查：发布工单、上线清单、CI
READY: Paid-team audience is approved in the release plan   就绪：付费团队受众已在发布计划中批准
MISSING: Security sign-off on the new external API change   缺少：新外部 API 变更的安全签字
NEXT: Ask the security owner to review, then recheck the checklist   下一步：请安全负责人评审后再查清单
```

如果提问者想要基于个人笔记的定制简报，Bot 可以在一对一里准备；频道只拿到对团队安全的结论和证据。这比一个自信地记着周一信息的 Bot 好得多。

## 发布 Bot 前先测试记忆层

第一个评测不该问 Bot 能不能回忆一个事实，而该问它是否在对的范围用对的事实。邀请团队前测五种情况：

```javascript
M01  私密偏好    → B 永远不会继承 A 的偏好
M02  共享决定    → B 看到决定，看不到 A 的聊天
M03  状态已变    → 当前来源优先于已存记忆
M04  说法冲突    → 不能悄悄改成新政策
M05  私人连接器  → 需要批准 + 适合频道的回答
```

要用两个真实团队账号来跑，而不是在负责人自己的聊天里跑两次，否则没测到真正重要的边界。每个案例记录提示词、预期行为、Bot 的回答和它用的来源。除了回忆准确率，还要追踪：

```javascript
wrong-scope saves             存错范围的次数
stale-fact actions            基于过期事实的动作
unsupported team claims       无依据的团队主张
approval bypasses             绕过审批
time to correct a bad memory  修正一条错误记忆所需时间
```

最后一项常被低估：任何共享记忆系统迟早会存错东西，关键是团队能否找到、修正，并知道它影响了哪些输出。作者的上线标准：私密泄露或未授权动作直接判失败；过期或无依据的回答要修复并重跑相关案例后，才能扩大使用范围。（这是建议标准，不是 Grok Bot 内置评测。）

## 当 Bot 学错了东西

问题不是会不会出错——一定会——而是错误能存活多久、修好前有谁看到。假设 Bot 因一次例外存了“所有企业续约都要 VP 批准”，一周后开始拖延普通续约。像处理小型数据事故一样：

1. 让 Bot 展示团队记忆，找到那条原话；Grok Bot 可以问它存了什么，再让它修正或删除；
2. 找出来源对话或决定、负责人，以及复用过这条记忆的工作；追溯不到来源，就别因为听起来合理而保留；
3. 先修正权威的续约政策，再删除或替换 Bot 的错误记忆；如果错误来自技能、文件或 Bot 描述，也一并修；
4. 用另一个同事的账号重跑续约案例，检查回答以及是否尝试了动作；
5. 复查错误记忆生效期间产生的草稿和工单。

最后一步最容易漏：删除记忆只改变未来行为，改变不了已经起草的邮件和已做的决定。可复用的经验是：在 Bot 之外为重要共享记忆保留轻量记录——主张、来源、负责人、范围、复查日期。Grok Bot 的记忆是工作上下文，你的台账才是审计记录。

## 最先会犯的错

- **把个人 Bot 直接复制成团队 Bot 却不审查记忆**：Grok Bot 提供团队副本，可以从头开始或排除私密内容，把这一步当作安全步骤，而不是配置麻烦；
- **把团队记忆当公司数据库**：Bot 应记住稳定上下文，重新打开会变的数据；
- **让所有人通过聊天改流程**：共享技能有负责人是有原因的；
- **忘了 Slack 里的工作在哪跑**：频道线程是共享环境，不是观众更多的私聊；
- **嫌 OAuth 慢就给 Bot 一个大权限服务密钥**：共享密钥会扩大 Bot 对每个同事的实际权限；
- **只统计“答了没有”，不看“范围对不对”**：Bot 可能答得很快，却泄露了私密细节或基于过期事实行动；
- **以为记忆是一次训练**：实际问题是 Bot 在之后的工作中能复用什么上下文，而不是底层模型权重有没有变。

## 作者真正会上线的配置

1. 一个团队 Bot 只做一件共享的工作，不做全公司通用助理；
2. 在 Bot 描述里写清职责和审批边界；
3. 只加必需的文件和插件；用户相关动作优先用个人 OAuth，共享数据用只读共享凭证；
4. 可重复流程写成技能，由负责人或指定管理员维护；
5. 只加少量已确认的团队记忆，每条都有明确来源或负责人；
6. 用不同账号测试个人笔记、过期事实、矛盾和 Slack 受众边界；
7. 先发布给小团队，检查失败，约定好怎么修正错误的团队记忆，再扩大范围。

这是“AI 同事”演示里看不到的部分：团队能教它，Agent 才有用；团队能说清它学了什么、从哪学的、什么时候该忘，它才可靠。

## 真正的转变

Grok Bot 最初的故事是“持久”：给 Bot 一份工作、工具、一台电脑和完成它的时间。团队 Bot 加了一个新问题：当 Bot 属于一个团队而不是一个人时会怎样？

答案不是更大的上下文窗口，而是一套记忆架构：

- 个人笔记放个人背景；
- 共享记忆放明确的团队知识；
- 维护中的团队技能放流程；
- 实时系统放会变的事实；
- 权限决定 Bot 实际能做什么。

边界划对了，一次纠正就能让下一个人的工作更好；划错了，Bot 会把一个错误放大到整个团队。这就是记忆工程重要的原因。
