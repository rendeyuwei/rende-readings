## 要点摘要

- Agent 让「问与答之间」压缩到秒级；模型越好，明显错误越少，输出读起来像样却不再逼你二看一眼——批判性思维不会自动发生，必须刻意排进日常。
- 光谱从上到下：认知卸载（cognitive offloading）→ 推迟判断（deferral）→ 认知投降（cognitive surrender）；信任或懒惰会让人悄然下滑，认知债 / 理解债（comprehension debt）往往在需要改系统时才暴露。
- 低代价处可整段下放；高后果处（产品方向、用户影响、能否安全上线）必须守住推理与问责。
- 瓶颈已从「写码」转向「确认自己对了」：给 Agent 验证手段，先看命令与输出再看摘要；绿勾只证明查了某一个属性。
- 前端塑问题、后端审输出：好提示是批判性思维；意图债（intent debt）只能自己还。产出超过你愿署名的量，就是编排税（orchestration tax）——你已在「希望」而非「审查」。
- 监督悖论（paradox of supervision）：监督模型恰恰需要那套可能因过度依赖 AI 而萎缩的技能；工作可卸载，问责不能。

---

从前，批判性思维被教成：带着谦逊的好奇与健康的怀疑接近新信息——听不同观点，形成自己的判断。这依然成立；但如今日常几乎没什么在逼我批判性思考了，因为大量工作都经 Agent 跑过。对那些已完全买入 agentic 工作流的工程师与产品人（并行多会话、期待模型越来越好），我想说：我很喜欢这些工具。写这篇文章，不是为了劝你们少用 Agent。

我的目标是：在一个很容易把任何事卸给 Agent 的世界里，帮你保住批判性思维。

过去，多数认知与审美加工发生在「问题」与「答案」之间的空隙里。那个空隙现在以秒计。Agent 用得越多，困难反而越大（却未必是人们预期的那种）：模型越强，明显错误的比例越低。许多（多数？）输出文笔不错、大体正确，却不会逼你再看一眼。

即便你一次跑很多 Agent，盯输出的仍只有一双眼。

你必须把批判性思维建进日常——默认情况下，没有什么会替你做这件事。

之所以难自纠，部分因为 agentic 工作流很舒服。忙碌一天里拿到又快又顺、常常还对的答案，确实解渴；也正因如此，警惕才容易松懈。

## 卸载、推迟与投降（Offloading, deferral and surrender）

和人聊这件事时，我把它描述成一条光谱：

最上端：认知卸载（cognitive offloading）——把任务委派给 AI，但仍对结果保有所有权。我整天都在这么做。你也应该。中间：推迟判断（deferral）——工具的输出变成你的新输入；结果不再是假说。最下端：认知投降（cognitive surrender）——AI 的输出悄悄变成「你自己的」，你觉得没必要核对。

Cognitive surrender 一词由沃顿的 Steven Shaw 与 Gideon Nave 提出。它很贴合我看到的现象：随着信任（或懒惰）上升，人会沿光谱往下滑。过渡很少被察觉，因为每一步都渐进、看起来都合情理。上一份答得好，下一份就略读。再下一份只扫骨架。然后有人问你某一行，你连在 Agent 帮助下也解释不清。

那就是认知投降。认知债（cognitive debt）就是这样累积的。通常要等到你试图套用某个系统心智模型、却发现它根本不存在时，才被发现。Margaret-Anne Storey 写过：团队里这会表现为对共享「系统理论」理解的侵蚀。我写过代码侧的对应物——理解债（comprehension debt，Jeremy Twei 提出的术语）。当下它完全隐形：代码库看起来干干净净，测试也过。直到你要改系统，才发现没人再懂它。对策略文档或规格，你只读了目录就签字，也一样。

说清楚：我不是在鼓吹不可能的事。维持大型现代代码库的完整心智模型本就不可能。Claude Code 团队公开说过，他们按需重建理解：需要懂某一块时，就让 Claude 解释那一切片，而不是把整棵模型塞进脑子。我以前也写过，这类债比多数工程师以为的更可恢复。你不必维持全量模型，只要能在需要时局部重建。你只需要知道自己缺什么。

利害低的地方，尽管整段下放。当你连在 Agent 帮助下也解释不了某个答案时，你已经交出了所有权。这也不总是问题。就在最近，我录课要在三家评分相近的酒店里选录制场地。我没空手动翻完所有评价，就把决定交给了 AI。效果不错，下次我还会这么做。但我不会在决定如何投资、如何给孩子职业建议，或在工作里——该做什么、什么改动影响哪些用户、是否安全上线——时这么干。错误代价低的地方接过交接；别人要承受后果的地方，把推理留在自己手里。

## 我问自己的问题（The questions I ask myself）

以前不确定自己怎么想时，我常回到这样一组基本问题：我怎么知道自己在做对的问题？怎么知道解法对？有没有证据支持结论？怎么知道已经做完？多数时候，就是谁、什么、哪里、为什么、何时、怎么。写出来显得幼稚得离谱，却逼你按本来会忽略的类别去想。如今太容易跳过这一切，直接问 Agent「你觉得我该怎么办」。下面是我现在问自己的新版问题。

**我有没有在提问前先形成假说？** 对任何非琐碎任务，在跑 Agent 前，我会写下——哪怕只在脑子里——我认为答案可能是什么。猜得烂也没关系。有了新信息随时可以改主意。可一旦读到写得很好的回应，就很难再想象别的可能性。若你毫无方向，可请模型做 Thariq Shihipar 所说的盲点扫描（blind spot pass）：把你已知的交给它，让它找出你的未知的未知。

**我是在请它帮我思考，还是在把思考从我身上卸走？** 两者都行，只要你清楚自己在做哪一种。

**要让这是错的，必须先成立什么？** 然后去查证。模型的自我置信评估，远不如你能实际跑的一次检验有价值——所以给它一次检验。

**我有没有从另一个角度听过反方？** 当我对某个偏开放的问题立场很硬时，我会让不止一个模型论证反方，再审输出、形成自己的意见。这更花时间，但对主题的了解会深得多。

**我会不会在必须维护它的人面前为此下注？** 这适用于代码，也适用于你交付的任何东西。我认为这是可问责性的标准。

**我不再练习什么？** 也许是一部分例行调试。我可以接受放下一些，但希望是有意为之。

## 把验证当成习惯（Verification as a habit）

我最近写了很多关于验证的内容，因为我认为瓶颈已从写码转向「确认自己对了」。当你给 Agent 验证手段——端到端测试、属性测试，或真实的应用交互——它就能改一改、跑验证、读输出、再试，而你还什么都没看。这就是 Boris Cherny 所说的「给 Claude 一条验证自己工作的路」；我认为这是拿到好结果最关键的一环。你不再逐行读，而是在建这些回路、审查证据。

你也可以把验证也投降掉。「有没有证据支持我的结论？」变成了「勾是不是绿了？」Agent 让写测试便宜到你会看到大量绿勾；也可能有一个通过的测试抓不住坏掉的功能。若测试与功能犯了同一错误，它会通过。而一个绿勾只传达一个属性。太容易想象它覆盖了一切。

对每一个绿勾，写明它查了哪个属性。再写明它没查哪个。

事先定义「已验证」——事后你会合理化任何结果。Agent 工作的终点线应是可触摸的：测试通过、截图、日志或 trace。这样完工标准是事实，而不是基于「看起来做完了」这种可投降的诠释。收到 Agent 完工通知时，先别看摘要：先看实际执行的命令片段及其输出。

Claude Code 也能（在新鲜上下文里用子 Agent）自我批评，当作健全性检查；值得写进回路，每次都跑，而不是只在你想起来时。我仍会在结尾问：「我漏了什么吗？」听起来傻，但常常：用前沿模型做完复杂功能、看过、审过，再问一句「漏了什么吗？」，它会再带回两三点。所以我总会问。

当然，这些不必成为常态；知道何时深挖是一种技能。Claude Code 团队代码评审文章里，我最喜欢的经验法则是：「若你说不出这些检查会漏掉什么，就要求真正评审，而不是快速批准。」

这也适用于代码之外。若 Agent 替你综合了五十次客户访谈或一份竞品分析，抽查几份源文档，确认摘要准确。核对你建议所依赖的那个数字，确认计算正确。

Agent 让验证变得便宜可建。对你难的是：知道什么样的验证才算好。

## 真的去注意生成出来的东西（Actually paying attention to what's generated）

假设 Agent 给你一份 600 行的 PR。你大致看了结构。没逐行读。变量名看起来合理，测试也过，于是批准了。但中间某处，事务边界里有个微妙的排序变化，或某个你从没想过的边界情况默认值被翻了。你大概算是审过了——但只审了你本来就知道会找到的东西。

写代码与审代码是不同技能；审到某一点就变成橡皮图章。所以：把 diff 当成不是 AI 写的来读，再越过 diff，看 Agent 替你做了哪些决定。长会话里它替你做了大量小决定：默认值、什么出范围、两条需求冲突时它如何重写其中一条。

摘要里说「一切顺利」时，你看不到这些；所以请它列出所做的决定与假设。然后考自己。随机挑几行：这一行呢？那一行呢？对文档：合上它，试着凭记忆写出主论点。有人有个我喜欢的长会话习惯：让 Claude 写一份变更报告，文末给你测验，规则是「测验满分才合并」。

充分理解你要交付的东西，好到能捍卫它。因为总有一天会有人问。

Agent 也可以守护你的注意力。例如，我有一个开源项目收到大量 PR。我会用 Agent 帮忙判断进来的是什么、哪些违背指南、哪里多半需要我的注意力。我很少让 Agent 自己最终裁定，但它们能收窄到我该聚焦之处，然后我才能真正思考：这些改动是否在用对的方式解对的问题。

还有量的问题，你必须对自己诚实。我称之为编排税（orchestration tax）：Agent 生成的东西，与你愿意署名的东西之间的落差。若完工工作堆积的速度快过你消化的速度，再开一个会话帮不上忙——直到你修好这一点：收紧检查，让更少的东西需要你；或者放慢速度。

当你产出的超过你能站台的，你就不再是在审查。你是在希望。

## 垃圾进，垃圾出？（Quality in, quality out）

人类心智模型仍在环路里，只是不在中间，而在前端与末端。你把精力放在任务描述与上下文的前端，以及审输出的后端。正因为如此，好输入对输出质量如此重要；我把好提示视为一种批判性思维技能。

历史上，你若提出含糊请求，有人会挑战你，你可能意识到：「哦等等，其实我还没想清楚。」Agent 往往不会在那里拦住你。它填上你漏掉的，交回一份看起来做完的东西，尽管背后的想法仍模糊。我把这写成意图债（intent debt）——可能存在于你并未亲写的产物里的隐含目标、约束与理由。与其他债不同，这一种没人能替你还。意图必须来自你。

你的提示反映你对问题的理解；若表达不清，可能是你自己心里也不清。

在求助前，用自己的话写请求简报。写清受众、出范围项、完工定义。若第二轮修正仍到不了，别再微调——重写提示。

也可以让 Agent 帮你做这件事。我喜欢 Andy Clark 对「委派给 AI」与「与 AI 协作」的区分。后者是互相放大的良性循环：提示磨利输出，输出磨利下一轮提示，也磨利你对问题的心智模型。若还不清楚，请 Agent 就它不懂的地方采访你。若合上会话时你自己的心智模型更清晰了，那就是成功的信号。

也要小心输入链路。很容易让每个 Agent 只把上一个 Agent 的摘要塞进上下文，很快第三个 Agent 根本没读过原文。

你还需要自己的输出标准。我在各种创作媒介里玩过 AI，多数从未示人，因为达不到我的标准。东西都格式漂亮、语气自信，所以「抛光感」不再是有用信号。

AI 或许让生产更快了；但若我不愿意把输出归到自己名下，我就不会把它发出去。

当某物不达标准时，把原因记进共享配置、hook 或测试，免得再发生。品味就这样复利；记下「为何没过线」本身就是好练习。

## 「但模型会比我更擅长这个」

若你像身边许多人一样对这片空间的未来很乐观，前面几节大概已经冒出这个念头。再过一两年，模型能检出我能检出的东西，何必还练这门技能？

在大量检出能力上，你可能是对的；我也一直主张把越来越多的检出推给 Agent。但我认为它仍重要的理由是：最终，总有人对上线之物负责。无论 AI 帮了多少，必须有人承担问责。

对给定任务信任 Agent 到什么程度，本身就是判断。保持校准的一部分，就是审工作——因为模型错的地方一直在变。Anthropic 对自己工程师与研究者的研究指出陷阱即监督悖论（paradox of supervision）：「监督 Claude 恰恰需要那套可能因过度使用 AI 而萎缩的编程技能。」

这些对我最重要、且更好的模型也解不了：你在建什么、为什么值得、影响谁、你愿意牺牲什么？这些问题需要你回答。Agent 可以帮忙想通，我也希望它帮忙；但最终仍是你的。

你可以卸载工作与大量审计，但不能卸载问责。

## 日常可嵌入的做法（Practices for the everyday）

不必样样严苛。挑适合你工作流的插进去。

每周一次，不靠 Agent 写一点代码，或做一件「若忘了怎么做会很糟」的真事。（我称之为校准练习，但不是道德练习。）每月一次，写下你停做了什么，并决定其中哪些你接受不再做。我旧博文里的一个问题仍然有效：若 AI 不存在，你会有多迷茫？

若某物超出理解，去学它。写作时碰到没见过的短语，我可以 Google 一行解释塞进去。我更愿稍做研究，真正理解它，好看见它落在何处。

认真核对机器是真工作；假装不然，团队就会不做。它不是免费的，所以排进日程当作一项，你才会真做。

你停止练习的技能会消失，而且可能比你猜的更快。继续做那些你不愿放手的。

## 带走什么（What to bring with you）

**要有意。** Agent 可以考你、采访你、出示证据，但只有你把它设好。所以设好。

**对自己在光谱上的位置诚实。** 若连在 Agent 帮助下也解释不了答案，你已经投降了。

**要有假说。** 提问前先形成，哪怕很烂。

**绿勾只意味着一件事。** 它查了什么？没查什么？

**找证据。** 先读它跑了什么、返回了什么，再读摘要。

**读，是为了知道它替你做了哪些决定。** 它替你决定了什么？

**打磨提示。** 你怎么写提示，显示你对问题理解了多少。

**设一条线，并守住。** 若你不愿署名，就不发出去。

**用手动练习那些你不愿丢掉的技能，让自己留在局里。** 可以这样做：提问前写下你认为会发生什么；Agent 做完后，写下它没检查的一件事。告诉我，这是否改变了你读输出的方式。独立思考。问更好的问题。对结果负责。
