## 没有验证，就只能亲自盯着

Claude Code 团队里，绝大多数代码（约 90%）由 Claude 编写并评审。到了这个规模，如何让 Agent 用证据验证自己的工作，就变得极其重要。验证闭环（verification loop）是扩大委派的基础：没有它，往往一次只能跑一两个 Claude，因为每件事都得自己查；有了它，才可能并行几十甚至上百个。这是对工作方式的判断，不是一项单独公布的实验结论。文中还提到一项内部测试：在结构化文件生成任务里，用独立的评分器（grader）按评分标准（rubric）检查结果，比标准提示循环最多高出约 10 个点，而且最难的题目提升最大。文中没有说明「点」的计算方式，也没有把这个结果推广到其他任务。

从前昂贵的验证——测试、基准、规格、真正的端到端运行——现在向 Agent 开口就要便宜得多；生成之后，这些材料会像软件一样运行，因而可以频繁执行，而不必消耗太多额外 token。结果也可以反过来改进它：例如反复在「检查日志里是否出现用户数据」这类测试上失败，就可以加一条钩子，或在 `CLAUDE.md` 里把规则写得更明确。这多半（mostly）能避免问题再犯，而不是每次都奏效。

## 并非所有测试都同等重要

无论选哪一类，都有失败方式要避开。测试若不稳定（flaky），等于在训练 Agent 再跑一遍，而不是去修失败的代码；测试若太慢，它在一批改动里能跑的次数变少，定位问题也更难；较重的测试，最好安排在提交改动之前进行。

若只能先关注一类，就选端到端（end-to-end）。它描述的是真实用户路径，比如把商品加入购物车、结账、进入确认页：很难被糊弄，功能要么整体成立，要么不成立，出了问题也能更具体地指出断在哪一步。单元测试更快、也更少抖动，但它们全部通过时，功能本身仍可能是坏的。文中用一张对照图说明：单元测试可能只报「30 秒后超时」；端到端测试却能给出截图，并说明是哪一步失败。

属性测试（property test）则是先写下你认为不该失败的陈述，再用测试库生成大量输入，试图证明你是错的。例如不变量（invariant）：账户余额不能变成负数。此外还有往返、幂等、等价等常见属性。因为输入不是按人的偏见逐条写出来的，这类测试很擅长抓住边界情况；在重写时，若规格已经偏离生产行为、不再能作为可靠的验证依据，它尤其有用。

差异测试（differential test）把旧系统当作判定标准（oracle）：给新旧两套实现同一批输入，看输出是否一致。它尤其适合大规模迁移、且行为应当保持不变的场合。关键是使用随机生成的输入，或生产流量的样本。

## Claude Code 团队怎样做验证

把改动真正跑起来，往往比再多写几个测试更重要。你不会在模拟器里都没试过，就把一次 iOS 改动发布出去；对 Claude 也是一样。给它做端到端冒烟测试（smoke test）的办法后，它会自己迭代，并更快抓住真正的错误——文中写到，这就是 Anthropic 内部几乎所有改动的测试方式。没人能读完每一处改动，他们用失败来决定哪些需要人看：Claude 先跑检查并尝试修复；若一轮检查在三轮之后仍失败，就停下来交给人。检查由代码负责人来写，并打磨到能标出负责人自己也会标出的问题；当检查把评审者拉进来时，应说明原因，免得对方只能从差异里自行推断。

他们维护一份含 39 项的可靠性清单，每项都有可从差异里读出的触发条件。Claude 读差异，只检查触发条件匹配的项，通常是 3 到 10 项。他们并不靠叠加更多评审者来提高质量，而是用一份 `REVIEW.md` 写明：对这份代码，评审者应当留意什么。各轮评审和验证也应建立在先前轮次和过去失败的上下文上，而不是每次都从头检查一遍。更硬的一条是：改动不能修改用来评判它的检查，否则检查就已经失效。代码评审应从基础分支或默认分支读取 `REVIEW.md`，而不是从本次合并请求的改动里读。对已经过时的提交，一次通过的评审并没有意义。较便宜的检查应放在前面；测试、构建和检查器，则应在开合并请求之前就跑完。新的门禁宜先从观察模式开始，再进入强制执行。

检查规则本身也要被检验。他们会追踪已合并改动里有多少被回退、有多少在合并前被负责人否决，以及规模相近、此后一直保持干净的改动子集。更正式的评估会用已合并且保持稳定的改动作为对照，以免过度报错；召回率（recall）会把原始发现、验证后的结果和最终评审分开统计，以便看出系统是否把已经找到的缺陷又弄丢了。漏检要变成规则时，他们会从人工评审意见和回退里抽取模式：至少在两个合并请求里出现过，并且能从差异里识别出来，才成为候选规则；然后由三个 Agent 试着反驳这些候选，再由人在合并请求里评审并批准。对不稳定的测试，Claude 不能跳过它们、加睡眠等待，或重试到通过为止；找不到根因，就删掉测试并写明原因。规则也要定期修剪，免得只增不减。

## 好测试，才会有好结果

把验证层也当成一套系统来对待：它不能被自己所评判的改动改写；要用对你真正重要的缺陷来检验它；漏掉的教训要写下来，免得再犯，也要修剪，让留下的条目仍然值得跑。做到这些，工作才会从读每一份差异，转向定义何谓完成、并审看证据——这也才是能同时跑许多 Claude 的原因。

## 编者解读

对做界面的人来说，最有用的未必是「再补一些测试」，而是承认：测试全绿，并不等于用户路径是通的。超时只说明失败，端到端截图却能指出断在哪一步。文中「约 90% 由 Claude 编写并评审」「最多高出约 10 个点」，是对团队实践和一项内部测试的陈述，不能直接外推到所有代码库；「10 个点」的算法原文也未说明。
