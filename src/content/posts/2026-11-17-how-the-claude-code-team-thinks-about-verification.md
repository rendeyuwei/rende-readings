## 1. 没有验证，就只能亲自盯着

Claude Code 团队里，绝大多数代码（约 90%）由 Claude 编写并评审。到了这个规模，作者认为关键不再是“要不要用 Agent”，而是如何让它用证据证明自己做对了。

他把验证闭环（verification loop）看作委派的基础：没有它，你往往一次只能跑一两个 Claude，因为每件事都得自己查；有了它，才可能并行几十甚至上百个。这是作者对工作方式的判断，不是一项单独公布的实验结论。

质量上，他引用了团队内部一次关于结构化文件生成的测试：用独立评分器按评分标准（rubric）检查 Claude 的产出，任务成功率比常规提示循环最多提高 10 分，而且最难的题目提升最大。这里的「10 分」是该次内部测试的上限，场景也只限于结构化文件生成，不能理解成给任何前端任务加一套测试就会有同样涨幅。

测试、基准、规格和真正的端到端运行，过去核验成本很高，现在可以交给 Agent 去生成；生成之后它们会像普通软件一样反复执行，不必每次都再消耗大量 token。闭环还可以反向改进 Agent：例如它反复通不过“日志里不得出现用户数据”这类检查，就可以加 hook，或在 `CLAUDE.md` 里写得更明确。作者的用词是这「多半」能避免同样的问题再出现，并不是保证永不再犯。

## 2. 若只能先做一类测试，就做端到端

无论哪类测试，都要避开两种失败模式：测试不稳定，等于在训练 Agent 再跑一遍，而不是去修代码；测试太慢，它在一批改动里能跑的检查变少，问题更难定位。更重的测试，作者建议放在提交之前做。

他最看重的三类测试，是端到端测试（end-to-end / E2E）、属性测试（property test）和差异测试（differential test）。若只能先投入一种，他选端到端：写的是真实用户路径，比如加购、结账、进入确认页。这类测试很难被“局部做对”糊弄过去，功能要么通，要么不通，也能更具体地指出哪里坏了。原文配图对比说，单元测试可能只报「30 秒后超时」，端到端测试却可以给出截图，并说明是哪一步出了问题。

单元测试更快、也更少抖动，但可能全部通过，功能仍然坏了——因为 Agent 和测试都没有理解完整任务。更有效的做法，是给 Agent 一双能操作、能观察真实运行系统的“手和眼”：用 skill 启动、驱动并检查应用，工具可以是 Chrome DevTools Protocol（CDP）、模拟器或 API 测试装置（harness）。功能地图（feature map）也可当作指南和评分标准，因为它通常从用户视角列出路径、快捷键、选择器和预期结果。

属性测试针对的，不是你事先想到的失败方式，而是人容易漏掉、Agent 也常在这里失手的边界。先写下你认为不会破的命题，再用测试库生成数千组输入去反驳，例如 JavaScript/TypeScript 的 fast-check、Python 的 Hypothesis、Rust 的 proptest。常见命题包括往返编码（round-trip encoding，编码后再解码应回到原文）、必须始终成立的不变量、做两次应和做一次效果相同的幂等（idempotency），以及优化实现应与朴素但正确的实现等价。这类输入不是由写代码的同一个 Agent 按自己的偏见构造的，因此更能把它“看住”；在规格已经偏离线上行为时，对重写尤其有用。

差异测试则把旧系统当作判定标准（oracle），特别适合功能应当保持不变的大规模迁移：同一批输入分别跑新旧系统，结果不同就说明有缺陷或破坏性变更。关键是使用随机生成的输入，或抽样的生产流量；还要归一化空白之类无关差异，并对“新环境本来就该不同”的情况保留已批准变更清单。

## 3. 先把改动跑起来，再让检查保持诚实

作者写得很干脆：把应用从头到尾跑一遍，比只跑测试更重要。你不会在模拟器里都没试过，就发布一次 iOS 改动；对 Claude 也应如此。他建议让 Claude 像人或测试工程师那样测完整应用：网页改动用 Claude 的 Chrome 扩展，移动端用 iOS 或 Android 的 MCP，桌面用计算机使用（computer use），后端则在本地把服务跑起来。启动和检查步骤可以写成名为 `verify` 的 skill，放进仓库的 `.claude/skills/`，并尽量靠近相关代码。作者说，Claude 知道在提交前使用这个 skill。接着要把它打磨得又快又稳，当作冒烟测试装置（smoke test harness）来看。他给出的判断是：在 Anthropic，他们几乎用这种方式测试所有改动。文中的具体命令和产品能力以原文当时为准，使用前仍应核对当前文档。

没人读得完每一次改动，所以失败本身就是在筛选哪些事需要人看。Claude 先跑检查并尝试修复；同一项检查连续三轮仍失败，它就停下来，把人请来。检查应由代码负责人自己写，并调整到能标出负责人也会标出的问题；一旦把人拉进来，还应说明原因。

如果一次改动能够修改评判它的那套检查，这套检查就已经失效。作者举例：Code Review 读取的是基准分支或默认分支上的 `REVIEW.md`，而不是这次 pull request 里的改动。对一份已经过时的提交给出“通过”，也等于什么都没证明。便宜的检查要先做；他们团队会在开 pull request 之前，先由 Claude 跑测试、构建和 linter。

新关卡不要一上来就阻断。他们会给每次提交打上验证方式的标记，其中包含 `none`，以便查出哪些提交根本没经过验证。若会话里没有 `/code-review` 或 `/verify`，提交门禁可以分为关闭、观察（observe）和强制（enforce）三种模式：观察模式只记录“本来会被拦住”的情况，强制模式才会真的阻断。同一会话里若已被拦两次，下一次会放行，以免 Claude 卡死——作者也写明，Claude Code 并不完美。

他们不靠叠加更贵的评审者来提高质量，而是打磨现有的那一位，并用 `REVIEW.md` 写明这段代码该盯什么。可靠性方面，他们维护一份 39 项清单，每项都有可从 diff 里识别的触发条件；Claude 只核对匹配的条目，通常是 3 到 10 项。检查本身也要被检查：追踪回滚、合并前被拒绝的改动，以及规模相近、事后保持干净的对照样本。更正式的评测在此前的[代码评审一文](https://claude.dev/blog/solving-code-review-at-anthropic/)里写过，召回率还会分开看原始发现、验证之后和最终评审，以免系统把已经找到的问题又弄丢。除了找得对不对，还要看重不重要：必须修、应当修，还是吹毛求疵（nit）。

漏掉的问题要变成规则，但有门槛：从人工评审和回滚里抽出的模式，至少要在两个 PR 中出现、且能从 diff 里识别，再由人审批。不稳定的测试不允许跳过、加 sleep，或重试到通过为止；若找不到根因，就删掉测试并写下原因。测试套件和各类说明只会越积越多，这些教训也要定期修剪。

作者的收束是：把验证层当作一套真正的系统来对待——不让它被自己评判的改动改写，用对你真正重要的缺陷来打分，漏了就记下来，并修剪这些教训。做到这些，工作就会从“读每一份 diff”转向“定义怎样算完成，并审阅证据”；也正因此，才可能同时运行许多个 Claude。

## 编者解读：前端更不能只看测试是否全绿

这篇文章和不久前同一作者谈“编程 Agent 让你开始做管理”是同一条线：能委派多少，取决于你能不能验证，而不取决于你能同时开多少个会话。对前端来说，这一点更具体。页面好不好用，往往不是单元测试能看见的；超时报错也不会告诉你，是支付表单没加载，所以“下单”按钮一直不可用。更值得先做的，是一条又快又稳的冒烟路径：把应用跑起来，走完关键用户流程，留下截图和步骤说明。功能地图里的路径、快捷键、选择器和预期结果，正好可以当作 Agent 的评分标准。

但不要把“加更多 E2E”理解成万能答案。不稳定或过慢的端到端测试，会训练 Agent 重跑或少跑；检查规则如果能被同一次改动改掉，验证就失去意义。原文里关于结构化文件生成“最多提高 10 分”的数字，也不能外推成前端任务的预期涨幅。先让一个真实页面路径形成可靠闭环，再谈并行更多 Agent，增加的才可能是证据，而不是待审的截图。
