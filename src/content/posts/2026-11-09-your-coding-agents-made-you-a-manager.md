> 原文：[Your coding agents made you a manager](https://x.com/addyosmani/status/2119332146485891501)（另有 [X 长文页](https://x.com/i/article/2118901185377964033)）

管编程 Agent（coding agent）的技能，几乎就是管团队的技能，而且不必先当经理才能学会。若你整天都在和它打交道——选任务、写说明、委派、跟进、评估结果、决定什么可以发布——你已经在做管理。真正用得好的，往往不是最会写提示词的人，而是学会了怎样管理的人。

这并不等于要你改头衔，也不等于 Agent 可以替代经理或同事。许多他所欣赏的工程师选择继续做个人贡献者（IC），是为了离工作更近，也见过朋友当上经理后消失在日程里。他所说的管理，是通过让别人做好自己的工作，来产出好的结果。你对糟糕经理的不满，也可以看成与 Agent 协作时的问题清单：含糊的交接、缺少上下文、期望一再改变，对模型同样有害。下文按他排列的影响大小展开。他此前也写过：Agent 同样需要管理者，以及所谓「认知投降」（cognitive surrender）。

## 先给它一条检查工作的路

最有效的一招，是给 Agent 一种能自己检查工作的办法，并让它把结果作为证据拿出来：测试、构建、截图，或其他能给出明确通过或失败的机制。要避免的，是把「看起来完成了」当成确认——若没有验证，这往往就成了它唯一的判断，人也会变成它的测试套件。对界面改动，可以把检查设成真正打开页面，迭代到可用、好看为止。能跑这些验证的那条命令，常常是 `CLAUDE.md` 里最有用的一行。验证也可以嵌进工作流，例如做完后继续跑测试直到通过，或把差异交给一个没见过当前对话的子 Agent 做评审。

## 把仓库里看不到的上下文说清楚

该写的，是它光看仓库无法知道的事：要达成什么、为什么重要、有哪些约束、什么不做、怎样才算成功。不要只丢下一行任务，也不要把说明书写成它读代码就能发现的内容。说清结果和约束，把「怎么做」留给执行的一方——他借用军中的「指挥官意图」（commander's intent），以及 Netflix 常说的「给上下文，而不是给控制」。他把一句含糊的「把仪表盘做快一点」改写成更完整的说明：目标、原因、约束、范围之外的事项，以及用哪条脚本给出前后数字，并标明其中数字只是示例。

## 让每次纠正都能累积下来

同一件事纠正过不止一次，就写进团队的 `CLAUDE.md`，或做成共享技能；过一段时间再看，新模型是否还需要这些纠正。要避免每个会话都手工改同一处，或把只存在于你这台机器上的隐性知识当成团队记忆。文件宜短，适合写入的是验证命令、代码里容易误导的地方、仓库里看不到的决定，以及已经纠正过两次的事。

## 默认交给它判断，只强制不能让步的事

默认让它自己决定；钩子、拒绝规则这类硬性执行，只留给必须永远做、或必须永远不做的少数事情。提示词和项目说明是可以权衡的请求，钩子和管理设置才是始终生效的要求。多数时候应让模型做判断，因为它看着真实代码，往往比预先写死的规则更知道某条指引现在该不该用。适合强制的，是「永远不要改生成出来的客户端」这类硬要求。把偏好写成全大写规则，或给可有可无的习惯上钩子，在他看来就是新的微管理。

## 动手前先对齐计划

先就计划达成一致，再让它写代码；读计划时要看隐含假设，并把任务切成互不重叠的部分。多个 Agent 同时做互相重叠的任务，看起来像并行，最后往往变成同一个合并冲突。计划够清楚时，模型常常能一次做完；更大的任务，可以把计划当作设计评审来看。分解之后，要检查切片是否重叠，并让共享接口先落地。

## 尽早纠偏，两次不行就重来

先看第一分钟，一看跑偏就纠正。若已经两次纠正都失败，就开一个新会话，用更好的提示词重来，而不是继续打第三次、第四次补丁。问题往往出在上游的说明、上下文或范围。回退若便宜，也可以先试一条更大胆的路，事后再把具有一般性的教训写下来。

## 能委派任务，不能交走判断

Agent 负责做事，产品取舍、安全边界、什么可以发布，仍由你来决定。对待每一份差异，都要像自己会因为它被叫起来处理故障那样。看见测试全绿、命名也还像样，就批准一份很大的差异，那不是代码评审，只是在为代码背书。他承认自己也差点掉进去：曾让 Agent 研究与竞品的差距并写出本地改动，自己读了调研、扫了一眼代码，差点推上去——那些改动会给用户增加复杂度，收益却很小。六百行差异，名字合理，测试是绿的，并不等于可以批准。

## 设计一套你不在也能跑的任务

在部署可自主运行的任务之前，先问清楚：怎样算做完，如何自检，边界在哪，护栏是什么（例如回合或花费上限），产物放在哪、谁来批准，尤其是不可逆操作。不要在没有完成定义和停止点的情况下，把一个长任务丢下去过夜。任何新流程，都宜先看过最初几次，再交给它无人值守。

## 扩大验证，而不是扩大盯梢

增加 Agent 的速度，不应快过检查、目标和新的评审者接手盯梢的速度；除了吞吐量，还要衡量质量。他称之为「编排税」（orchestration tax）：过了最初几个，每再加一个，需要的注意力往往比上一个更多。他自己多数日子会跑四五个后台 Agent，再加几个本地会话，有些日子这就已经太多——这是个人实践，不是通用配额。无法靠盯得更多来扩展数量，只能靠需要盯得更少；周期时间、回退和返工，也比「AI 写了多少代码」更有用。

## 先决定什么不做

先问谁需要它、怎样知道它奏效、什么情况下该停。因为「做起来很便宜」，就把每个说得通的想法都做成合并请求，会变成一只杂物抽屉，团队还得继续评审和维护。实现变便宜之后，更该问的不是「能不能做」，而是「该不该做」。

## 这套类比在哪里会失效

能同时跑五个 Agent，并不等于已经准备好管理五个人。管人更难，动机、冲突、职业发展和信任建立并没有对应物，这些技能也不会原样迁回去。另一方面，向 Agent 返工几乎是免费的，也可以让它先做出几种方案再比较。它们往往积极且自信：好工程师被要求做错事时会反驳，Agent 更可能照做，人也更容易过度信任。他提到沃顿商学院关于认知投降的研究：参与者多数时候会接受有缺陷的 AI 答案，而且变得更自信；对策之一，是让 Agent 反驳自己的答案。初级开发者仍需要训练，发布、值班和职业发展也仍是人的事。

## 你并不需要经理这个头衔

好的资深工程师早就在做这些事：写清设计、交代上下文、认真评审，并让周围的人变得更好。关键不在头衔，而在于成为「好代码被写出来」的原因。有了 Agent，这种练习来得更快，做错了也可以撤回。你不必想成为经理；但能把 Agent 用好的工程师，往往已经在这个过程中学会了管理。

## 编者解读

这篇文章把「会用 Agent」拉回到一套可检查的动作：先能验证，再并行；把仓库外的意图写清楚；让纠正沉淀下来；计划先于实现；两次纠不回来就重写请求。尤其值得记下的，是他差点把「该不该做」一并交出去的那次经验：测试全绿，并不等于可以批准一份很大的差异。判断、问责和签字，仍然在人这边。
