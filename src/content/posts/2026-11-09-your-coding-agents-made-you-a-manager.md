## 1. 不是让你转岗，而是重新看待交接

选任务、交代要求、委派、跟进、验收、决定上线——天天使用编程 Agent，你其实已在做这些管理工作。作者说的管理，是**通过支持他人的工作取得好结果**，不是劝工程师放弃技术路线，也不是说 Agent 能替代同事。

交接的重点，是补足仓库里看不到的信息：为什么做、会议定了什么、有哪些限制、什么不做、怎样才算完成。代码里能查到且 Agent 会去查的内容，不必重复塞进说明。探索性任务可以先宽后细，不需要每次都写成完整规格。

## 2. 先让它能验证，再让它独立干活

作者把可执行验证放在首位。测试、构建、类型检查，以及 UI 的实际页面检查，都能缩短“实现—发现问题—修正”的循环。交付时还要展示证据；只听一句“看起来做完了”，等于让人成为 Agent 的测试系统。

验收也必须具体。原文用仪表盘性能任务示范：说明组织成员规模、p95 加载时间、不能改的接口和验证办法。**其中的规模与耗时数字只是示例，不是实测成绩或通用指标。**

无人值守更要预先约定完成条件、验证方式、权限边界、回合或费用上限，以及产物交到哪里、哪些不可逆动作需人工批准。并行规模只能随验证能力增长，不能靠人更卖力地盯屏幕。

## 3. 把反复纠错变成共同规则，别把偏好变成禁令

同一问题纠正不止一次，就写进团队的 `CLAUDE.md`；重复流程可以沉淀成共享 skill。这样下次不必重讲，经验也不会只留在某个人的会话里。说明要简洁，模型更新后还应检查旧规则是否仍有必要。

但书面要求不等于强制控制。作者主张，只有“必须发生”或“绝不能发生”的少数硬要求，才值得用 hook、拒绝规则等机制落实；普通偏好留给 Agent 根据具体代码判断。把所有喜好都写成大写命令或钩子，是另一种微观管理。文中具体命令和默认行为属于当时工具的例子，使用前仍应核对当前版本。

## 4. 把方向纠偏前移，别用更多提示补救坏交接

编码前先对齐计划，审查隐藏假设；并行任务要避免重叠，共用的接口应先完成。开工后尽早看方向，不要等大量代码写完才发现理解错了。

作者给出一条经验规则：**两次纠偏都失败，就带着已学到的信息重写要求，开启新会话**，而不是继续追加第三、第四轮补丁式提示。这不是“两次报错就丢弃成果”，而是提醒人检查上游的说明、背景和范围。

## 5. 能委派实现，不能交走判断

测试全绿，只能帮助验证实现，不会替人决定产品是否值得做、安全边界是否合理、什么应当上线。作者要求人保留这些判断与责任，并把改动控制在能真正理解的范围内。

判断产出也不能只数 PR 或 AI 写码比例；还要看交付周期、返工和回退。实现越便宜，越需要决定什么不做，否则省下的编码时间会变成长期维护负担。

这套类比有边界：Agent 返工相对便宜，也更容易自信附和；多个会话可能共享同一模型的盲点。带人还涉及激励、冲突、职业发展和长期信任，运行五个 Agent 不等于会带五个人，团队合作与新人的基本功训练也不能因此被挤掉。

## 编者解读：真正要减少的是监督负担

这篇文章的价值，不是给“多开几个 Agent”找理由，而是把效率问题改成一个交接问题：任务能否说清，结果能否查验，关键决定由谁负责。先让一个小任务形成可靠闭环，再考虑扩大并行；否则增加的可能不是产能，而是待审的工作。
